# Рабочий процесс перевода и публикации

## Входные данные и результат

Для выполнения необходим URL оригинальной статьи. Параметры по умолчанию и ограничения заданы в `SKILL.md`. Перед созданием файлов проверь рабочее дерево.

## Пакет из нескольких статей

Запрос с двумя или более URL считай пакетом. Общие параметры запроса применяй ко всему пакету, а явно указанные параметры конкретной статьи — только к ней.

Веди каждую статью как независимую единицу работы:

1. создай для неё отдельную рабочую копию оригинала;
2. полностью закончи перевод и контроль качества;
3. создай и проверь её MDX и изображения;
4. зарегистрируй публикацию и проверь связанные ссылки;
5. только после успешного завершения переходи к следующему URL.

Не объединяй исходные тексты, заметки, изображения и неоднозначные терминологические решения разных статей. Не переноси перевод неоднозначного термина из одной статьи в другую без проверки контекста и словаря.

Если доступны субагенты, для пакета или сложной длинной статьи назначь независимую содержательную проверку. Проверяющий должен получить оригинал, готовый перевод, словарь и требования раздела «Контроль качества перевода», но не предполагаемый список ошибок. Основной агент рассматривает замечания, исправляет подтверждённые расхождения и повторно проверяет затронутые места. Технические операции с общими реестрами координирует основной агент, чтобы избежать конфликтующих правок.

Ошибка или недоступность одной статьи не отменяет уже готовые публикации и не должна останавливать остальные статьи, если они не зависят от неё. В итоговом сообщении отдельно укажи результат каждой статьи и ясную причину для каждой незавершённой.

Получай оригинал один раз. После успешного извлечения сохрани полный текст, метаданные, ссылки и список изображений в рабочей копии по [инструкции кеша](source-cache.md). Переводи и сверяй результат с этой копией. Повторно обращайся к источнику при пропусках, неясностях или явном запросе обновления; результаты загрузок и проверок перенаправлений используй повторно в пределах задачи.

Не перечитывай неизменившиеся справочники в одной задаче: проверка результата не означает повторное чтение инструкций. Словарь и канонические теги пока читай целиком — они небольшие.

Для поиска внутренних и внешних ссылок используй два реестра в корне репозитория через помощник выборки ниже; не загружай их целиком в контекст:

- `translated-articles.md` — опубликованные переводы;
- `external-links.md` — ещё не заменённые внешние ссылки из переводов.

При проверке дубля и замене ссылок используй [инструкцию выборки](registry-lookup.md). Читай её один раз при первом поиске; получай только совпадения, требующиеся текущей статье.

## Размещение статьи

Создай файл:

```text
src/content/posts/<category>/<slug>.mdx
```

Допустимые категории:

- `articles`
- `translations`
- `cored20rpg`
- `core-d20`
- `sage-advice`
- `srd`
- `forgotten-realms`
- `marwang`

Для обычного перевода используй `translations`.

Slug сформируй из английского названия или источника статьи:

- lowercase;
- kebab-case;
- без даты;
- короткий, но однозначный;
- расширение `.mdx`.

До создания проверь, нет ли файла с таким slug, строки с тем же canonical URL в `translated-articles.md` и ссылки на тот же оригинал среди публикаций. Не создавай повторный перевод и не перезаписывай существующую публикацию без прямого указания пользователя.

## Frontmatter

До заполнения frontmatter прочитай только определение `posts` в `src/content/config.ts` и используемые им зависимости. Не загружай схемы других коллекций. Соблюдай действующую схему проекта; помощник проверки читает её локально.

Базовая схема:

```yaml
---
title: "Русское название статьи"
description: "ПЕРЕВОД - Краткое естественное описание без хэштегов, не длиннее 400 символов вместе с префиксом"
date: YYYY-MM-DDTHH:mm:ss+03:00
tags:
  - Перевод
  - Канонический авторский тег
  - Тематический канонический тег
author: Имя автора оригинала
translator: Codex по инструкциям Антона "Palant" Палихова
cover: ~assets/covers/<slug>.<расширение>
---
```

Правила заполнения:

- `date` — текущие дата и время публикации перевода в формате ISO 8601: `YYYY-MM-DDTHH:mm:ss±HH:mm`. Следует указывать фактические дату, часы и минуты на момент создания статьи, включая смещение часового пояса. Например: `2026-10-06T00:08:00+03:00`;
- `author` — имя автора оригинальной статьи в исходном написании;
- значение `author` должно иметь ровно одно соответствие авторскому тегу в `tag-system.md`;
- `translator` — значение из текущего запроса, иначе `Codex по инструкциям Антона "Palant" Палихова`;
- `description` — естественное русское описание до 400 символов, начинающееся с `ПЕРЕВОД - `, без хэштегов;
- `cover` добавляй только при наличии подходящего главного изображения оригинала;
- `draft` не добавляй;
- не добавляй `source`, `originalUrl`, `category` и другие отсутствующие в схеме поля.

Если действующая схема проекта расходится с приведённым примером, соблюдай `src/content/config.ts`, не добавляя самовольно новые поля.

## Теги

Полностью прочитай `tag-system.md` и используй только перечисленные там канонические теги.

- Первым обязательно поставь `Перевод`.
- Одним из тегов обязательно поставь ровно один тег из раздела «Авторские теги переводов». Он должен соответствовать точному значению `author` по таблице «Соответствие авторов переводов тегам».
- Если точного значения `author` в таблице нет, добавь один новый уникальный канонический авторский тег и строку соответствия. Не подменяй автора тегом сайта или издательства.
- Не добавляй в одну статью авторские теги других авторов. Варианты написания имени одного автора могут ссылаться на один тег, но один тег не может обозначать разных авторов.
- Затем выбери тематические теги так, чтобы всего получилось 3–6 тегов.
- Обычно используй от 3 до 6 тегов.
- Для игровой системы используй не более одного основного тега.
- Не создавай синонимы, варианты написания или английские версии существующих тегов.
- Не делай тегами конкретные заклинания, существа, города, NPC и номера сезонов.
- Тег сайта или издательства не заменяет обязательный авторский тег.

## Ссылка на оригинал

Сразу после закрывающего разделителя frontmatter добавь отдельной строкой:

```md
[Оригинал](<canonical URL статьи>)
```

Если исходный URL перенаправляет на canonical URL, используй canonical URL. Удали якоря, UTM-метки и прочие параметры отслеживания. Ссылка обязательна.

## Словарь терминов

Используй словарь, прочитанный по `SKILL.md`; при его изменении обнови соответствующие сведения.

- Применяй заполненные записи с учётом значения термина, игровой системы и редакции. При совпадении контекста специальная запись имеет приоритет над общей.
- Соблюдай следующий приоритет: явные указания текущего запроса → словарь → официальная или устоявшаяся терминология → самостоятельный перевод по контексту.
- Используй выбранный вариант последовательно в заголовках, описании, основном тексте, таблицах, подписях и alt-текстах. Допускай необходимые склонения и согласование; учитывай примечания к записи. Правила канонических тегов остаются обязательными.
- Пустой словарь, пустые строки и записи без перевода не ограничивают выбор терминов. Для отсутствующих терминов используй правила раздела «Заклинания и игромеханические сущности». Не дополняй и не исправляй словарь автоматически: пользователь ведёт его вручную.
- Словарь определяет перевод термина, но не отменяет правило указания оригинала при первом содержательном упоминании игромеханической сущности.

## Перевод

Переведи содержимое статьи полностью, без сокращения, пересказа или добавления отсутствующих у автора рассуждений.

Сохрани:

- структуру и порядок материала;
- заголовки;
- абзацы;
- списки;
- цитаты;
- таблицы;
- примечания;
- содержательные ссылки;
- подписи изображений;
- выделения;
- блоки кода.

Не включай меню сайта, навигацию, рекламу, рекомендации, комментарии читателей, формы подписки, кнопки социальных сетей и иные элементы, не относящиеся к статье.

Пиши естественным литературным русским языком, сохраняя авторский тон и избегая буквального копирования английского синтаксиса. Переводи обращение `you` по контексту и придерживайся выбранного стиля во всей статье.

Не переводи URL, команды, программный код, имена API и файлов, обозначения игровых систем и имена собственные без устоявшегося русского варианта.

Сохраняй содержательные гиперссылки оригинала. Не оставляй внешних ссылок на изображения.

## Контроль качества перевода

Для каждой статьи выполни три раздельных прохода. Не совмещай содержательную сверку с технической проверкой MDX.

### 1. Полный перевод

Переведи все содержательные элементы оригинала по правилам раздела «Перевод». Не сокращай повторения, оговорки и примеры только потому, что они кажутся избыточными. Не улучшай аргументацию автора и не добавляй пояснения от себя.

### 2. Сверка с оригиналом

Последовательно сопоставь перевод с сохранённой рабочей копией оригинала. Проверь каждый заголовок, абзац, пункт списка, цитату, таблицу, примечание, подпись, alt-текст и содержательную ссылку. Нельзя ограничиваться общим перечитыванием статьи.

Исправь:

- пропущенные или добавленные сведения;
- изменение причинно-следственных связей и логических переходов;
- ошибки в отрицаниях, модальности, числах, единицах измерения, именах и ссылках;
- неточную передачу терминов, идиом, шуток, метафор и авторских оговорок;
- неоправданное усиление или смягчение утверждений автора;
- сверяй перевод терминов с словарем проекта;
- непоследовательные переводы одного термина в одинаковом контексте;
- потерю форматирования, которое влияет на смысл или структуру.

Особенно проверяй короткие служебные слова и конструкции, меняющие смысл: `not`, `unless`, `except`, `only`, `may`, `must`, `should`, сравнения, диапазоны и ссылки на предыдущие части текста.

### 3. Русская редактура

После содержательной сверки перечитай перевод отдельно как самостоятельный русский текст. Устрани:

- буквальные кальки и английский порядок слов;
- тяжёлые или двусмысленные конструкции;
- неясные местоимения;
- неоправданные повторы, канцелярит и стилистические разрывы;
- скачки между обращением на «ты», «вы» и безличной формой;
- несогласованность терминов в заголовках, тексте, таблицах, подписях и alt-текстах.

Редактура должна улучшать русский язык, не меняя факты, степень уверенности, авторский тон и ход рассуждений. После смысловой правки повторно сверь изменённый фрагмент с оригиналом.

Не считай успешную автоматическую проверку MDX подтверждением качества перевода. Публикация готова только после всех трёх проходов.

## Заклинания и игромеханические сущности

При первом содержательном упоминании каждого заклинания или значимой игромеханической сущности после принятого русского перевода укажи оригинальное название курсивом в круглых скобках.

Примеры:

- огненный шар (*fireball*);
- волшебная стрела (*magic missile*);
- спасбросок Ловкости (*Dexterity saving throw*);
- Класс Защиты (*Armor Class*);
- черта Великий мастер оружия (*Great Weapon Master*);
- состояние «схваченный» (*grappled*);
- легендарное действие (*Legendary Action*).

Правило распространяется на:

- заклинания;
- классы и подклассы;
- черты;
- особенности классов и существ;
- действия, реакции и бонусные действия;
- состояния;
- навыки и характеристики;
- спасброски;
- игровые параметры;
- магические предметы;
- игровые процедуры;
- названия правил и подсистем;
- другие термины со специальным значением в правилах.

Применяй следующие ограничения:

1. Оригинальное название добавляй только при первом содержательном упоминании термина.
2. При повторных упоминаниях используй только русский вариант.
3. Оригинальное название внутри скобок выделяй курсивом.
4. Не добавляй вторые скобки, если автор уже указал оригинальный термин.
5. Не дублируй общеизвестные аббревиатуры D&D, AC, DC, HP, NPC и CR, если расшифровка не нужна для понимания.
6. В заголовках используй естественное русское название без перегрузки скобками; оригинал добавь при первом упоминании в основном тексте.
7. Сначала применяй словарь терминов по правилам выше; если подходящей записи нет, проверяй официальную или принятую русскую терминологию D&D. Не придумывай новый перевод при наличии устойчивого.
8. Если устойчивого русского перевода нет, предложи точный вариант и сохрани оригинал в скобках.
9. Названия конкретных произведений, игр, сеттингов и персонажей сами по себе не считаются игромеханическими сущностями.

## Изображения

Для загрузки используй `scripts/download-images.mjs` по [справке помощников](helpers.md). Он возвращает готовые локальные пути; выбор содержательных изображений и лучших исходников выполни по правилам ниже.

Скачай все содержательные изображения статьи в `public/images/` и называй последовательно:

```text
<slug>-1.<ext>
<slug>-2.<ext>
<slug>-3.<ext>
```

Продолжай нумерацию, если изображений больше трёх. В MDX используй локальные ссылки:

```md
![Осмысленный переведённый alt-текст](/images/<slug>-1.<ext>)
```

Требования:

- выбирай наиболее качественный вариант из `srcset`, `picture`, `data-src` или ссылки на исходный файл;
- сохраняй исходный формат, если нет причины его менять;
- переводи подписи и alt-тексты;
- не скачивай логотипы, аватары, рекламу, кнопки и декоративные элементы;
- проверяй MIME-тип каждого скачанного файла;
- расширение файла должно соответствовать содержимому;
- не перезаписывай существующее изображение с другим содержимым;
- после локализации не оставляй внешних ссылок на изображения.

Главное изображение дополнительно сохрани как:

```text
src/assets/covers/<slug>.<ext>
```

И укажи во frontmatter:

```yaml
cover: ~assets/covers/<slug>.<ext>
```

Если у статьи нет подходящего главного изображения, не добавляй `cover` и не создавай искусственную обложку.

## Внешние файлы

Найди содержательные внешние ссылки на загружаемые файлы: документы, таблицы, архивы, раздаточные материалы и другие файлы, являющиеся частью статьи.

Для каждого доступного файла:

1. Скачай файл в `public/files/downloads/`.
2. Определи имя по `Content-Disposition` или конечному URL после перенаправлений. Сохрани исходное расширение, если оно соответствует фактическому формату.
3. Проверь MIME-тип и содержимое. Не сохраняй HTML-страницу, страницу ошибки или форму авторизации под видом файла.
4. Не перезаписывай существующий файл с другим содержимым. Совпадающий файл переиспользуй; при конфликте выбери однозначное имя.
5. Замени все внешние ссылки на этот файл в переводе внутренними ссылками:

   ```text
   /files/downloads/<имя-файла>
   ```

6. Сразу после первого упоминания файла добавь с новой строки один компонент:

   ```mdx
   <File
       file="<имя-файла.расширение>"
       title="<название файла> (<РАСШИРЕНИЕ>)"
   />
   ```

Требования к компоненту:

- добавляй не более одного `<File>` для одного файла в пределах статьи;
- `file` должен точно совпадать с именем файла в `public/files/downloads/`;
- `title` должен быть понятным русским названием и оканчиваться расширением в верхнем регистре, например `(PDF)`, `(DOCX)` или `(ODS)`;
- не дублируй расширение, если название уже оканчивается соответствующей пометкой;
- отделяй компонент от окружающего текста пустыми строками;
- локализованные файловые URL не добавляй в `external-links.md`.

Если файл недоступен, требует отсутствующих прав или не может быть надёжно восстановлен, не создавай поддельную замену. Оставь исходную ссылку, внеси её в `external-links.md` и укажи проблему в итоговом сообщении.

## Внутренние ссылки

Проверь все содержательные абсолютные ссылки статьи по `translated-articles.md`. Нормализуй URL для сравнения так же, как canonical URL: убери якорь, параметры отслеживания и необязательный завершающий `/`; считай варианты `http`/`https` и `www`/без `www` эквивалентными только после проверки, что они ведут на одну страницу.
- Если оригинальная ссылка присутствует в реестре, возьми путь из поля «Полная ссылка» и замени абсолютный URL внутренней ссылкой вида `/posts/<category>/<slug>`. Сохрани исходный текст ссылки. Якорь переноси только если соответствующая цель существует в переведённом MDX.
- Если перевода нет, оставь исходную ссылку без изменений.
- После замены не добавляй этот URL в `external-links.md`.

## Реестр переведённых статей

Для обновления обоих реестров и точечных замен ссылок используй режимы `preview`, `apply` и `check` помощника `scripts/publish-article.mjs` по [справке помощников](helpers.md). Не переписывай эти операции для каждой публикации. Правила ниже определяют результат; при неподдерживаемой конструкции помощник остановится с конкретной ошибкой.

После создания и проверки нового MDX добавь в `translated-articles.md` одну строку формата:

```md
| Original article title | Переведённое название | Original Author | Имя переводчика | <https://example.com/canonical-article-url> | <https://cyborgsandmages.com/posts/category/slug> |
```

Заполни поля следующим образом:

- «Оригинальное название» — точное название исходной статьи на языке оригинала;
- «Переведённое название» — значение `title` из frontmatter;
- «Автор» — значение `author` из frontmatter;
- «Переводчик» — значение `translator` из frontmatter;
- «Оригинальная ссылка» — тот же canonical URL, который указан в обязательной ссылке `[Оригинал]`;
- «Полная ссылка» — `https://cyborgsandmages.com/posts/<category>/<slug>` без завершающего `/`.

Не добавляй строку до создания MDX. Не создавай дубликаты по оригинальной или полной ссылке. Экранируй `|` внутри значений как `\|`, заменяй переносы строк пробелами и сохраняй строки в лексикографическом порядке по оригинальной ссылке.

## Реестр внешних ссылок

Используй `external-links.md` в корне репозитория как реестр содержательных внешних ссылок из переводных статей.

### Обновление старых статей после нового перевода

1. Нормализуй canonical URL переводимой статьи: убери якорь, параметры отслеживания и необязательный завершающий `/`; учитывай перенаправления и эквивалентные варианты `http`/`https` и `www`/без `www` только после проверки, что они ведут на одну страницу.
2. Найди этот URL в реестре. Сравнивай нормализованные адреса, а не только буквальное написание.
3. Если запись найдена, после создания нового MDX замени указанный внешний URL во всех перечисленных файлах на внутренний путь нового перевода вида `/posts/<category>/<slug>`. Сохрани исходный текст ссылки. Якорь переноси на внутреннюю ссылку только если соответствующая цель действительно существует в новом MDX; иначе убери его.
4. Проверь каждый изменённый файл поиском: внешний URL переводимой статьи больше не должен оставаться в содержательных ссылках. Не заменяй обязательную ссылку `[Оригинал]` в самой публикации перевода.
5. Удали из записи пути, в которых внешняя ссылка заменена или уже отсутствует. Если путей не осталось, удали весь раздел URL. Если ссылка по-прежнему должна оставаться внешней, сохрани соответствующий путь.

### Добавление ссылок из нового перевода

После окончательной правки нового MDX собери из него все сохранённые содержательные `http`/`https`-ссылки и внеси их в реестр:

- используй canonical URL без якорей и параметров отслеживания;
- не добавляй обязательную ссылку `[Оригинал]`, локальные ссылки сайта, локализованные файлы, изображения, навигацию, рекламу, ссылки YouTube (`youtube.com`, `youtu.be`, `youtube-nocookie.com` и их поддомены), другие социальные сети, профили автора, формы подписки и прочие несодержательные ресурсы;
- для каждого URL укажи путь к новому MDX в обратных кавычках;
- один URL должен иметь один раздел, а путь статьи под ним — встречаться один раз;
- если URL уже есть, добавь путь к существующей записи; не создавай второй раздел;
- сохраняй разделы URL в лексикографическом порядке, а пути внутри записи — в лексикографическом порядке.

Формат:

```md
## <https://example.com/canonical-article-url>

- `src/content/posts/translations/article-with-link.mdx`
- `src/content/posts/translations/another-article-with-link.mdx`
```

Реестр отражает фактическое состояние файлов: не добавляй URL, которого нет в указанной статье, и не оставляй путь после удаления или замены ссылки.

## Требования MDX

- Не используй HTML без необходимости.
- Экранируй конструкции, способные сломать MDX, особенно `<`, `>`, `{` и `}`.
- Для URL со скобками используй `[текст](<URL>)`.
- Не добавляй несуществующие импорты и компоненты.
- Начинай иерархию заголовков с `##`: название уже выводится из frontmatter.
- Не повторяй название статьи заголовком `#`.

## Проверка

Выполни `publish-article.mjs validate` перед регистрацией и `publish-article.mjs check` после неё по [справке помощников](helpers.md). Успешные автоматические проверки повторять вручную не нужно. Смысл, полноту перевода, выбор терминов и содержательность ссылок проверь отдельно. Сборку проекта не запускай.

Проверь отчёт помощника: категория и frontmatter, ровно один соответствующий авторский тег, остальные канонические теги, оригинал, файлы изображений и их форматы, внутренние ссылки и согласованность реестров. При ошибке повтори только затронутый этап после исправления.

Дополнительно проверь:

- каждый файл из `<File>` существует в `public/files/downloads/`;
- внешние ссылки на успешно загруженные файлы заменены внутренними;
- для каждого локализованного файла в статье присутствует ровно один `<File>`;
- ссылки на локализованные файлы и YouTube отсутствуют в `external-links.md`.

Сверь полный перевод с сохранённой рабочей копией оригинала. Проверь контекст и единообразие терминов по словарю, включая заголовки, описание, подписи и alt-тексты; сохрани все содержательные элементы.

Перед регистрацией статьи явно зафиксируй для себя, что выполнены все три прохода из раздела «Контроль качества перевода». Если независимый проверяющий нашёл расхождения, не регистрируй статью до исправления подтверждённых ошибок и повторной сверки затронутых мест.

## Итоговое сообщение

Для одной статьи укажи:

- путь к MDX-файлу;
- русский заголовок;
- автора оригинала;
- переводчика;
- выбранные теги;
- canonical URL оригинала;
- путь к обложке либо факт её отсутствия;
- список добавленных изображений;
- список статей, в которых внешние ссылки на новый перевод заменены внутренними, либо факт отсутствия таких замен;
- количество внешних URL, добавленных в `external-links.md`;
- полную ссылку, добавленную в `translated-articles.md`.

Для пакета сгруппируй эти сведения по статьям и добавь краткую сводку: сколько статей опубликовано, сколько осталось незавершёнными и почему. Не представляй пакет полностью завершённым, если хотя бы одна статья не прошла содержательную или техническую проверку.
